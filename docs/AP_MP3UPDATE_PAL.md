# MP3Update and Disable Deflicker on PAL (T35)

**Recommendation.** Port Disable Deflicker as a standalone PAL option. The four PAL video-mode records match the NTSC-U records at a different address. Defer the full MP3Update port until the author can share a PAL build or the underlying edits. The ten PAK diffs need PAL-specific resource changes and repacking. The two supplied discs are standalone Wii `RM3E01` and `RM3P01`, both disc 0, revision 0.

## Per-diff results

All eleven target files exist at the same paths in the two data partitions. Every PAL target differs in both size and SHA-256 from its NTSC-U counterpart. HDiffPatch 4.6.9 applied all eleven diffs to clean NTSC-U files and rejected all eleven clean PAL files with exit code 6 (input size differs from the size recorded in the diff).

The size column shows the compressed `.hdiff` size and the measured NTSC-U target size change, in bytes. The resource counts represent distinct type/asset-ID pairs per PAK. The example offsets are absolute within the extracted file, in **NTSC-U original → PAL original** order. `MREA` is room data and scripting, `MLVL` is the world layout, `SAVW` describes save data, and `STRG` holds strings. **Resource port** means the existing binary diff cannot be ported by shifting offsets. The underlying edit can be recreated on PAL by asset ID and, for room scripts, layer and instance ID. Rebuild the PAL container around those edits, preserving its localized assets, asset order and duplicate copies. Copying over an NTSC-U PAK would discard PAL-only changes. Cases with matching base resources are good candidates for a selective port. Cases with a differing base need a three-way comparison of clean NTSC-U, updated NTSC-U and clean PAL.

Allow roughly **20–36 person-days** for all ten PAKs from binaries, plus **3–5 days** for integrated testing. The work includes rebuilding PAKs, checking localized text and running the AP patcher and PrimeHack through touched progression, pickup and save paths. Elysia carries the widest dependency and progression changes. These are planning estimates based on the observed changes. An author-supplied edit list or PAL project could reduce the manual work.

## Disable Deflicker addresses

The 28 byte changes all lie in initialized DOL data (section index 12 in the 18-entry header, data section 5 using zero-based data-section numbering). The DOL header and both executable text sections are byte-identical before and after patching NTSC-U. Each affected record matches the structure of a `GXRenderModeObj`, with `vfilter` at record offset `0x32`. The seven coefficients change from `08 08 0A 0C 0A 08 08` to `00 00 15 16 15 00 00`. Their sum stays at 64 and the weights on adjacent lines go to zero. The two neighboring NTSC and EURGB60 progressive-mode records already contain the latter coefficients. The mode labels below follow the mode IDs and dimensions. [libogc render-mode structure](https://github.com/devkitPro/libogc/blob/master/gc/ogc/gx_struct.h) · [libogc mode definitions](https://github.com/devkitPro/libogc/blob/master/libogc/video.c)

| Video record (mode ID) | NTSC-U filter DOL offset / RAM | PAL filter DOL offset / RAM |
| --- | --- | --- |
| NTSC 480i (`0x00`) | `0x5A20EA` / `0x805A600A` | `0x5A46EA` / `0x805A860A` |
| MPAL 480i (`0x08`) | `0x5A2162` / `0x805A6082` | `0x5A4762` / `0x805A8682` |
| PAL 528-line interlaced (`0x04`) | `0x5A219E` / `0x805A60BE` | `0x5A479E` / `0x805A86BE` |
| EURGB60 480i (`0x14`) | `0x5A21DA` / `0x805A60FA` | `0x5A47DA` / `0x805A86FA` |

Each range covers seven bytes starting at the given offset. The PAL port should verify the four original records before writing and smoke-test PAL 50 Hz and PAL 60 Hz output in Dolphin/PrimeHack. T35 verified the addresses offline. A PAL runtime result remains untested.

## Reproduce the comparison

1. Read the disc ID, disc number and revision at ISO bytes `0x00–0x07`. Extract the eleven targets from each data partition into a scratch directory outside the checkout. T35 used `retro-data-structures` 0.28.0 `GameDisc` with its FST reader for the PAKs and `get_dol()` for the DOL. All 22 extracted files also matched the earlier WIT extracts byte for byte by SHA-256.
2. Use the checked-in `randovania/data/gollop_mp3_patcher/MP3Update` diffs. Every diff was compared byte for byte against the same entry in the author's v7.2 ZIP. Run `hpatchz -info DIFF` and apply each diff with `hpatchz ORIGINAL DIFF OUTPUT` to each region in scratch space. Compare sizes and compute SHA-256 on both originals and the NTSC-U outputs. [MP3Update v7.2 archive and Readme.txt changelog](https://github.com/MrMiguel211/MP3Update/releases/download/MP3Update_v7.2/MP3Update_v7.2.zip)
3. For each PAK, read the named table and the RSHD index using the layout in [savw_parser.py](../apworld/tools/savw_parser.py). Group entries by type and 64-bit ID, including duplicate copies. Compare sets of payloads after removing outer CMPD compression and routine `0xFF` alignment padding. For differing rooms, compare the decompressed MREA sections and script layers. Base-match counts describe those normalized resources. Reference resolution and gameplay behavior need separate verification. Feature descriptions use the author's changelog where the binary comparison gives structure but no player-facing meaning.
4. For the DOL, compare byte by byte. Map each edit through the section offset, load address and size arrays at `0x00`, `0x48` and `0x90`. Match the full 60-byte video-mode records in PAL data and check their original filter bytes.
